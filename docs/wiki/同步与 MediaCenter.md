# 同步与 MediaCenter

「高级」页签（需开启实验性功能的部分会标注）里有一组把**站点数据搬进本地库**的任务；MediaCenter 是它们的下游。

## 全量投稿遍历入库

把站点的视频列表按页遍历、解析并写入本地 IndexedDB 视频库（含 unlisted / private 的解析）。

- **可暂停 / 继续 / 停止**：控制意图写在后台内存里，真正生效在**页间闸门**上——已经在飞的那一页请求会跑完，硬取消既救不回时间，也会让游标与「已处理」集合对不上。
- **断点续跑**：每成功一页就把游标写进 `storage.session`。进程被杀（关浏览器 / 扩展更新 / 休眠）之后，主按钮变成「继续（第 N 页起）」，旁边另有一颗「从头开始」。
- 停止走的是「保留断点」的收尾，所以「停在 N 页、下次继续」这句话是真的；自然收尾且一页不缺才删游标。
- 进度写快照（`storage.session`），页面订阅 `onChanged` 实时渲染——不用轮询消息，因为长任务期间的消息往返不受扩展控制，卡住一次进度条就停在旧值。

## 订阅流同步

订阅流**没有游标**：它由到达 `/videos` 时自动触发、追平当月即停。两套判据并存只会互相打架，所以它只服务于 [[私有与不公开视频]] 的回填。

## MediaCenter 联动（实验性）

把本地缓存的视频元数据推送到 [MediaCenter](https://github.com/dawn-lc/MediaCenter)，方便在本地媒体库里检索。

### 配置

1. 「高级」页签开启实验性功能。
2. 填 MediaCenter API 地址（如 `http://localhost:3000`）与 Bearer Token。

### 同步分两个阶段

| 阶段             | 做什么                                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一、认领已有记录 | 按 `?page=&limit=100` 分页扫描远端列表，用 `fileHash`（其次标题里的 `[ID]`）把远端记录与本地视频建立映射；只索引「还没有映射」的本地视频，全部映射完成时一个远端请求都不发 |
| 二、推送元数据   | 6 条并发 worker 把本地完整记录 `updateMedia` 到远端；进度写快照，阶段切换立刻可见                                                                                          |

### 反向补齐（`BACKFILL_MEDIA_CENTER`）

常规同步只处理「库内已有视频」，而扫描导入的存量在本地库里没有对应记录，所以它们一次都不会被推送。反向补齐改用**远端记录自带的 iwara 视频 ID**（`fileHash` 优先，其次标题方括号）反查：

- **本地库优先**：批量入库刚刷过库，本地有 `full` / `partial` 记录就直接用，站点不可用（未登录 / 限流）也能补。
- 本地没有才去站点解析，且**只取视频页**，不拉文件源、不拉评论——两万条就是几十万次请求，绝不能那么干。
- 写回一律用**远端自己的 `filePath`**，不会用本机路径模板覆盖成不存在的路径。
- 跳过判据落在「这一条远端记录」上，不是「这个视频有没有映射」：同一个视频被改名重传成两条记录时，两条都会被补完元数据。
- 幂等可续跑：推送成功才写映射，失败的下次自动重试。

### 进度与中断

两条 MediaCenter 任务都是 fire-and-forget：消息只回 `{ started, reason? }`，整轮任务在后台跑，终态结论（总数 / 成功 / 失败 / 跳过 / 全局原因）也写进快照，页面据此渲染结果徽章。页面挂载时取一次归一后的初值——上一轮被打断就明确写「已中断」，不会永远转圈。

## 三条纪律（适用于上面所有长任务）

1. 启动是**同步占位**的：消息处理器立刻返回「已开始」，任务用 `void` 起，绝不在消息里 `await` 整轮。
2. 运行真相在**后台内存**里；进程没了任务也就没了，这一条 MV3 无法消除。
3. 收尾顺序固定：先 `await` 写终态快照，**再**释放内存标记。反过来会留下「内存已空、存储仍写 running」的窗口，下次启动就会把刚跑完的那轮判成「中断」。
