# 调试通道（本地桥）

排查「后台到底在做什么」时，最痛苦的是 MV3 的 service worker 在浏览器里跑：要等它出问题，再去扩展页手动点，日志还经常已经被回收。调试通道把这件事反过来——**扩展主动连本机的一个小服务**，把队列、扫描记忆、后台日志推过去，服务那边还能下发少量安全命令。

## 1. 形态与边界

| 项   | 取值                                                                       | 为什么                                                                                                                          |
| ---- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 传输 | 扩展 **主动** 长轮询 `POST http://127.0.0.1:PORT/poll`                     | 出站请求用现成的 `<all_urls>` 主机权限即可，不必改 manifest；MV3 的 SW 随时会被杀，长轮询每次请求独立，没有「断了要重连」的状态 |
| 方向 | 只出站，扩展**不监听端口**、不接受入站                                     | 少一个攻击面；也避免和用户的 aria2 / 其他服务抢端口                                                                             |
| 默认 | **关闭**（`debugBridgeEnabled: false`）                                    | 默认打开＝未经同意把调试数据往本机送，不该是默认值                                                                              |
| 命令 | 白名单：`snapshot` `scan` `retry` `rebuild` `remove` `logs`                | 只读状态 + 对队列的显式操作；**不执行任意代码、不改配置**                                                                       |
| 脱敏 | 键名形似 `token/secret/password/cookie/authorization` 的字符串一律变 `***` | 调试数据只在 127.0.0.1 上走，但也不该把凭据写进文件                                                                             |
| 频率 | 成功 3 秒一次，失败退到 15 秒                                              | 服务没起时不刷屏；正常时足够实时                                                                                                |
| 停止 | 配置关掉后循环自行退出（令牌递增），不残留定时器                           | 调试通道本身不该成为新的「神秘后台任务」                                                                                        |

## 2. 怎么用

1. 起服务（本机，任选端口，默认 8765）：

    ```bash
    node scripts/debug-bridge-server.mjs 8765
    ```

2. 扩展「高级」页 → **调试通道（本地）** → 打开开关，端口填 `8765`（改端口后两边要一致）。
3. 服务日志出现 `[bridge] 扩展已连接：<版本> / chrome-mv3` 就通了。

| 端点                        | 用途                                                                    |
| --------------------------- | ----------------------------------------------------------------------- |
| `GET /`                     | 人看的摘要：连接状态、版本、队列计数、失败任务前 30、警告/错误日志      |
| `GET /summary`              | JSON 摘要（agent 读这个，不把 800 多条任务灌进上下文）                  |
| `GET /state`                | 最近一次完整快照 + 命令回执（含每条的 `ok/error`）                      |
| `GET /command?command=scan` | 下发命令（也可 `POST /command` + `{"command":"retry","taskId":"..."}`） |

快照同时落盘到 `temp/debug-bridge-state.json`（`temp/` 已 gitignore），关掉页面也能事后读。

## 3. 快照里有什么

`version` / `runtime`（确认用户真的装上了新构建）、`config`（脱敏）、`tasks`（完整队列，含 `detail` 与 `kindRef`）、`counts`（按状态计数）、`scanMemory`（`storage.session` 里的扫描记忆：退避、熔断、卡住采样——「为什么它没动静」的答案基本都在这）、`logs`（后台 `console.info/warn/error` 的环形缓冲，最近 200 条）、`alarms`（定时器还在不在）。

日志环是通过包一层 `console` 收集的：**只抄一份，原样转发**，调试通道挂了也不影响原有日志。

## 4. 命令执行

命令随下一次轮询回给扩展（`{ commands: [...] }`），扩展执行完把 `{ id, ok, error?, data? }` 放进**下一次**轮询的 `results` 里，服务端按 `id` 对上。这样即使 SW 在命令执行到一半被杀，也不会出现「不知道到底做没做」——下次连上时结果要么已经回来，要么命令根本没被取走。

## 5. 不做的事

- 不做 WebSocket（省掉协议栈与重连状态机，MV3 里没有收益）；
- 不做「远程改配置」「远程执行代码」（一个调试后门不值得）；
- 不把调试数据发到 127.0.0.1 以外的任何地方；
- 不在默认构建里打开。
